# Phase 4 — 上下文预处理（设计说明，**未实现**）

> 状态：设计稿。代码没有任何改动，本文档交给后续实现者。
> 先读 [AGENTS.md](../AGENTS.md) 了解现有插件的结构与不变量。

## 1. 要解决的问题

总窗口现在能把一句话投递到正确的会话（Phase 1–3），但**投递的是用户原话**。真实使用里，原话经常不自足：

| 用户实际输入 | 目标会话需要知道什么 |
|---|---|
| “再画一条” | 上一条画的是什么、什么风格 |
| “接着上次那个改” | 上次改到哪、改的是什么 |
| “这个报错怎么办” + 一大段日志 | 日志对应哪个版本、之前试过什么 |
| 粘贴 30KB 配置文件 | 真正要看的是其中哪几行 |

目标会话收到“再画一条”时只能自己瞎猜，或者回头翻历史。**Phase 4 就是把这一步补上：投递前，把用户输入变成目标会话可直接执行的任务描述。**

## 2. 非目标

- 不做答案质量评估，不做模型裁判。
- 不修改会话历史（一个字节都不改）。
- 不跨工作区搬运上下文（默认禁止，见 §5.4）。
- 不改变 Phase 3 的路由判定（路由只决定“发到哪”，预处理只决定“发什么”）。

## 3. 硬约束（违反任何一条都算实现失败）

1. **缓存不变量**：历史消息必须逐字节保持原样；新增内容只能**追加在最后一条用户消息的末尾**。改前缀会让云端前缀缓存整段失效——这是成本上一票否决的事。
2. **延迟预算**：本地计算 < 800ms；需要调模型的路径必须可关且默认关，且 > 2s 直接放弃。
3. **成本预算**：每次投递新增 token ≤ 2K。按峰值价约 +$0.0006/轮。
4. **失败必降级**：任何一步失败都回到“原样发送”，并给出一行可见说明，不阻断投递。
5. **可撤销**：确认条里必须能看到“最终会发什么”，并有一键“按原文发送”。

## 4. 三个候选方案

| 方案 | 做法 | 收益 | 代价 | 建议 |
|---|---|---|---|---|
| **A. 检索补全** | 从目标会话历史取相关片段，追加在消息末尾 | 解决指代与“接着上次”，缓存安全 | 需要读历史；片段可能跑偏 | **主方案** |
| **B. 改写** | 用小模型把输入改写成自包含描述 | 表达更完整 | 5–20s 延迟、可能编造、默认关 | 可选开关 |
| **C. 剪枝** | 对用户粘贴的超长内容做摘要/截断 | 省 token、降噪声 | 丢信息风险 | 仅对超长输入触发 |

三者可以叠加，但**先做 A**。B 和 C 各自独立开关，第一版不实现。

## 5. 方案 A 详细设计

### 5.1 触发条件

全部满足才触发：

- 开关“预处理”打开（默认关，见 §6）；
- 输入长度 ≥ 8 字；
- 目标会话已确定（`target` 非空）；
- 目标会话历史条数 ≥ 2（新会话没有可检索内容）。

### 5.2 检索源

优先级从高到低：

1. **目标会话自己的历史**（默认，也是唯一默认允许的来源）；
2. 同工作区其它会话（默认关，需单独开关）；
3. 跨工作区（**不提供**，除非以后有显式的、按工作区选择的白名单）。

理由：把 A 工作区的内容塞进 B 工作区的会话，既是隐私问题，也会让目标会话产生错误前提。

### 5.3 数据从哪来（**待实现者验证**）

以下接口名来自对 `app.asar` 的阅读，**未在运行时验证过**。实现第一步是先写一个最小探针，在 `test/selftest.cjs` 的假环境里确认签名，再在真实环境确认：

| 候选 | 出处 | 需要确认什么 |
|---|---|---|
| `reference.binding.session` | `sessions.using` 的 reference | 是否暴露历史读取方法 |
| `ctx.remote.session.page(...)` / `session/history` | 会话控制器的 Remote 端点 | 分页参数、返回记录形状 |
| `SessionSnapshot` 的 history 投影 | 客户端 Session 对象 | 是否只含当前窗口、能否向后翻页 |

**不要**用 `ctx.sessions.search(query)` 代替：它是跨会话检索，不保证覆盖目标会话的最近上下文，也不能按轮次取。

### 5.4 抽取规则

- 只取 `user` 与 `assistant` 的 **text** 内容；
- 跳过 `reasoning`（思考过程不该被搬运）、跳过 `tool` 结果（噪声大、体积大）；
- 每条消息截断到 400 字；
- 优先最近 `K = 8` 轮；更早的只在相似度足够高时纳入。

### 5.5 打分与选择

复用现有的 `normalize` / `bigrams` / `overlapScore`（Phase 3 已在用）：

```
score(message) = overlapScore(用户输入, message.text) * 0.7
               + recencyWeight(message) * 0.3
```

- `recencyWeight`：最近一轮 1.0，每往前一轮衰减 0.85；
- 取 `score ≥ 0.15` 的前 3 条，总长 ≤ 1.2K token；
- 全都不达标就不追加（宁缺勿滥，与 Phase 3 的阈值哲学一致）。

### 5.6 组装格式

追加在**最后一条用户消息的文本末尾**，不新开消息：

```
<用户原文>

---
参考上下文（来自本会话较早的对话，可能不完整）：
- [3 轮前] 用户：画一条蓝色的鱼，胖一点
- [2 轮前] 助手：已生成，主色 #4D6BFE，身体接近正圆
```

设计要点：

- 明确标注“可能不完整”，避免模型把片段当权威事实；
- 每条带轮次偏移，便于模型判断时序；
- 分隔符用 `---`，与用户正文天然分界；
- **不要**把这段放进 system，也不要写成额外的一条 user 消息——两者都会改变消息结构，前者影响更大。

### 5.7 数据流

```
用户输入 ──► 触发判定 ──► 取目标会话最近 K 轮 ──► 抽取纯文本
                                              │
                                              ▼
                                       打分 + 截断
                                              │
                                              ▼
用户原文 + 参考块 ──► 确认条展示 ──► deliver(target, finalText)
```

`deliver()` 仍是**唯一**投递出口（见 AGENTS.md 不变量 2）。

## 6. UX

- composer 里加一个开关“预处理（附加上文）”，默认**关**——第一版不应该悄悄改变用户发出的内容；
- 确认条（已有）展示最终全文，超出 6 行就滚动；
- 顶部小字标注差异：`原文 + 2 段参考（+312 token）`；
- 提供“按原文发送”按钮，一键绕过预处理；
- 预处理失败时确认条照常出现，只是差异标注变成 `原文（未附加）`。

## 7. 失败模式与降级

| 失败 | 处理 |
|---|---|
| 读不到历史（权限/接口不存在） | 原文发送，状态行写“无法读取会话历史” |
| 历史为空 / 全是 tool 结果 | 原文发送，不提示（属于正常情况） |
| 打分全部低于阈值 | 原文发送，状态行写“未找到可参考的上文” |
| 客户端计算超时（> 800ms） | 放弃追加，原文发送 |
| 模型改写超时（若启用 B） | 放弃改写，回退到 A 或原文 |
| 目标会话属于另一工作区 | 只允许本会话历史；跨区片段一律不取 |

## 8. 成本与延迟（引用既有实测）

- 2K 新增 token ≈ **+$0.0006/轮**（DeepSeek 峰值价，缓存未命中口径）；
- 前缀不变，所以缓存命中率不受影响；
- 纯客户端检索：~10ms 量级，可忽略；
- 本地 8B 改写一次：**5–20s**（4070S，16K 上下文），因此 B 默认关、且不适合逐轮触发。

> 参考：`../tools/eval_prune.py` 曾量化过“压缩上下文 vs 直接发送”的账单差异；结论是**改写前缀会打掉缓存，得不偿失**，这也是本文档把“只追加”列为硬约束的原因。

## 9. 测试计划

纯函数（新增，放 `test/selftest.cjs` 的纯函数区）：

- 抽取：reasoning / tool 被跳过，text 被保留并截断；
- 打分：明显相关 > 无关；阈值边界；
- 组装：格式稳定、轮次偏移正确、长度上限生效；
- **不变量**：给定历史 `H`，输出 payload 的前 `len(H)` 条与 `H` 完全相等（深比较）。

集成（假环境）：

- 历史 mock 返回 3 条，输入“再画一条”，断言最终文本包含参考块；
- 历史接口抛错 → 原文发送且状态为降级文案；
- 开关关 → 输出与输入完全一致。

人工验收（必须在真实 DSH 里做）：

- 发“再画一条”，目标会话能正确理解用的是上一条的内容；
- 连续两轮，第二轮命中缓存（可用 whale-widget 或 usage 数据核对）。

## 10. 验收标准

1. 开关关闭时，行为与 Phase 3 完全一致（零回归）。
2. 开关打开、历史可读时，输入“再画一条”能在确认条里看到参考块。
3. 任何失败路径都不会阻断投递。
4. 历史前缀逐字节不变（测试断言）。
5. 新增 token ≤ 2K，且确认条如实标注。
6. 跨工作区数据不会被读取（代码层面无此路径，而不是靠开关）。

## 11. 明确不做

- 不做自动新建会话（那是另一个功能）。
- 不做多轮 agent 式预加工（多一次模型调用 = 多一份延迟与钱）。
- 不把参考块写进会话历史（它只存在于这一次请求里）。
- 不在插件里做向量库（工作区级检索已由宿主 `sessionQuery` 承担）。

## 12. 交给实现者的第一步

1. 在 `test/selftest.cjs` 里加一个假 `reference.binding.session.history()`，先确定**你希望的**签名；
2. 到真实环境里找到对应实现（会话控制器 Remote 端点或 Session 投影），对照确认；
3. 签名对不上就以真实为准，回来改假对象；
4. 再实现 `extractMessages` / `scoreMessages` / `composePayload` 三个纯函数；
5. 最后接进 `SessionOverviewPage`，保持 `deliver()` 单一路径；
6. 补测试，跑 `node test/selftest.cjs`，全绿再提交。

> 如果第 2 步发现客户端**拿不到**会话历史，方案 A 就不可行。退路是按 §4 的顺序降级：先做 C（只处理超长粘贴，纯客户端可做），B 需要接本地模型，最后再考虑请求宿主补接口。
